## __SOLID 원칙__

### __SOLID 종류__
자 그럼 SOLID 원칙에 대해 간단하게 살펴보도록 하자.

먼저 SOLID는 이니셜을 따서 만들어졌다는 사실을 안다면 알 수 있듯 5가지의 원칙이다. <br>
<br>
한글로 직역해서 말해주자면 <br>
1. 단일 책임 원칙
2. 개방폐쇄원칙
3. 리스코프치환
4. 인터페이스 분리 원칙
5. 의존 역전 원칙
<br><br>
이렇게 5가지가 있는데 세상 바쁜 사람을 위해 내가 느낀 것을 요약식으로 먼저 이야기를 하겠다. 하지만 나는 Unity를 하기 때문에 내가 하는것에 빗대어 이야기를 하겠다.

---

### __SOLID 요약__
- 단일 책임 원칙(Single Responibility)
   - 클래스가 한 가지의 작업만을 수행, 오지랖 ㄴㄴ 


- 개방 폐쇄 원칙(Open-Closed)
   - 이미 작동하는 방식을 변경하지 않고도 클래스의 기능을 확장가능해야함


- 리스코프치환(Liskov Substitution)
   - 하위 클래스는 부모 클래스의 방향성을 유지한 상태로 기본 클래스를 대체 할 수 있어야 한다. (가훈을 지켜야함)


- 인터페이스 분리 원칙(Interface Segregation)
   - 인터페이스를 작게 유지(사소한 느낌), 클라이언트는 필요한 것만 구현해야 한다.
   

- 의존 역전 원칙(Dependency Inversion)
   - 추상화에 의존, 하나의 구체 클래스에서 다른 클래스로 직접 의존 금지 ( 음식은 젓가락으로 먹기 이런느낌 )
<br>

이렇게 라고 생각한다. 이것만 보고 완벽하게 이해한다면 그 사람은 나보다는 일단 똑똑한 사람이다. 바쁜 사람은 가고, 내가 잊을 때 다시 보기위해 상세히 정리를 시작해보도록 하겠다.

### __단일 책임 원칙(Single Responibility)__

먼저 예시코드를 보여주고 시작하겠다.

#### ___단일 책임 원칙 예시코드-1___
```
public class UnrefactoredPlayer:MonoBehaviour 
{
	[SerializeField] private string inputAxisName;
	// 누를 인풋 시스템 이름
	[SerializeField] private float positionMultiplier;
	// 위치값에 곱할 수
	
	private float yPosition;
	private AudioSource bounceSfx;
	
	private void Start()
	{
		bounceSfx = GetComponent<AudioSource>();
	}
	
	private void Update()
	{
		float delta = Input.GetAxis(inputAxisName) * Time.deltaTime;
		yPosition = Mathf.Clamp(yPosition + delta, -1,1);
		// yPosition + delta의 범위 를 한정 짓고, yPosition에 대입
		transform.position = new Vector3(transform.position.x,
                                     yPosition * positionMultiplier,
                                      transform.position.z);
	}
	
	private void OnTriggerEnter(Collider other)
	{
		bounceSfx.Play();
	}
}
```

보기에 어떤 생각이 드는가? 사실 나같은 초보자는 별 생각이 없다. <br>
그냥 뭐 움직이이고 부딪히면 소리나는 정도 아닌가? 라는 생각이 들 것이다.<br>

하지만 요약을 봤다면 알 수 있을 것 이다. 이 코드는 움직임도 나타내고, 소리도 나타낸다는 것을 알 수 있다. 고로 이 코드는 `단일 책임 원칙`을 지키지 않은 코드이다.<br>

그렇다면 어떤식으로 바꾸어야 할까? 바로 예시코드 먼저 보여주도록 하겠다.

#### ___단일 책임 원칙 예시코드-2___
```
[RequireComponent(typeof(PlayerAudio),typeof(PlayerInput),
typeof(PlayerMovement))]

public class Player:MonoBegaviour
{
	[SerializeField] private PlayerAudio playerAudio;
	[SerializeField] private PlayerInput playerInput;
	[SerializeField] private PlayerMovement playerMovement;
	
	private void Start()
	{
		playerAudio = GetComponent<PlayerAudio>();
		playerInput = GetComponent<PlayerInput>();
		playerMovement = GetComponent<PlayerMovement>();
	}
}

public class PlayerAudio:MonoBegaviour
{ ... }
public class PlayerInput:MonoBegaviour
{ ... }
public class PlayerMovement:MonoBegaviour
{ ... }
```

어떠한 차이가 있는지 한눈에 알 수 있을 것이다. <br>
왜냐하면 클래스가 그냥 복사가 되 듯 많아졌기 때문이다.<br>
어 뭐야? 이렇게 많아지면 할 것만 많아지고, 더 어려운 것 아닌가요? NoNo 코드를 계속 짜다보면 진짜 내용이 너무너무 많아지고, 계속 추가해야 할 것이 생기기 마련이다.<br><br> 만약 예시-1 코드를 진행했을 경우에는 내용이 늘어나면 늘어날수록 어떤 곳에 어떤 코드를 짰는지 알 수 없을 뿐더러 찾기위해서는 너무나도 눈이 아프더라. 나의 눈이 안좋은 것에 충분한 일조를 했을 것 이다. <br>

주먹구구식이 아닌 이론적으로 이야기를 풀어나가 보자면 이 원칙은

#### __이론적 설명__
- 위와 같이 모든 클래스는 하나의 책임만을 가진다.
- 클래스는 그 책임을 완전히 `캡슐화` 해야 한다.
- 클래스가 제공하는 모든 기능은 이 책임과 부합해야한다.

`캡슐화` 관해서는 나중에 따로 상세히 설명을 할 것이기에 간단하게 설명하자면 클래스가 그 책임을 너~무 아껴야한다 라고 생각하면 된다.
누구나 소중한 물건, 소중한 것이 있지않은가?  만약 누군가가 빌려달라 했을 때 빌려줘야 한다면 내 눈앞에서, 나를 통해, 이러한 절차가 있는 것과 같다. 이 책임은 무조건 나를 통해서만!

아무튼 단일 책임 원칙은 이정도인 것 같다. 오늘은 그만 적고싶으니 내일 적도록 하겠다.
