## __SOLID 원칙__

### __SOLID 종류__
자 그럼 SOLID 원칙에 대해 간단하게 살펴보도록 하자.

먼저 SOLID는 이니셜을 따서 만들어졌다는 사실을 안다면 알 수 있듯 5가지의 원칙이다. <br>
<br>
한글로 직역해서 말해주자면 <br>
1. 단일 책임 원칙
2. 개방폐쇄원칙
3. 리스코프치환
4. 인터페이스 분리 원칙
5. 의존 역전 원칙
<br><br>
이렇게 5가지가 있는데 세상 바쁜 사람을 위해 내가 느낀 것을 요약식으로 먼저 이야기를 하겠다. 하지만 나는 Unity를 하기 때문에 내가 하는것에 빗대어 이야기를 하겠다.

---

### __SOLID 요약__
- 단일 책임 원칙(Single Responibility)
   - 클래스가 `한 가지`의 작업만을 수행, 오지랖 ㄴㄴ 


- 개방 폐쇄 원칙(Open-Closed)
   - 이미 작동하는 방식을 변경하지 않고도 클래스의 기능을 `확장가능`해야함


- 리스코프치환(Liskov Substitution)
   - 하위 클래스는 부모 클래스의 `방향성`을 유지한 상태로 기본 클래스를 대체 할 수 있어야 한다. (가훈을 지켜야함)


- 인터페이스 분리 원칙(Interface Segregation)
   - 인터페이스를 작게 유지(사소한 느낌), 클라이언트는 필요한 것만 구현해야 한다.
   

- 의존 역전 원칙(Dependency Inversion)
   - `추상화`에 의존, 하나의 구체 클래스에서 다른 클래스로 직접 의존 금지 ( 음식은 젓가락으로 먹기 이런느낌 )
<br>

이렇게 라고 생각한다. 이것만 보고 완벽하게 이해한다면 그 사람은 나보다는 일단 똑똑한 사람이다. 바쁜 사람은 가고, 내가 잊을 때 다시 보기위해 상세히 정리를 시작해보도록 하겠다.

### __단일 책임 원칙(Single Responibility)__


먼저 예시코드를 보여주고 시작하겠다.

#### ___단일 책임 원칙 예시코드-1___
```
public class UnrefactoredPlayer:MonoBehaviour 
{
	[SerializeField] private string inputAxisName;
	// 누를 인풋 시스템 이름
	[SerializeField] private float positionMultiplier;
	// 위치값에 곱할 수
	
	private float yPosition;
	private AudioSource bounceSfx;
	
	private void Start()
	{
		bounceSfx = GetComponent<AudioSource>();
	}
	
	private void Update()
	{
		float delta = Input.GetAxis(inputAxisName) * Time.deltaTime;
		yPosition = Mathf.Clamp(yPosition + delta, -1,1);
		// yPosition + delta의 범위 를 한정 짓고, yPosition에 대입
		transform.position = new Vector3(transform.position.x,
                                     yPosition * positionMultiplier,
                                      transform.position.z);
	}
	
	private void OnTriggerEnter(Collider other)
	{
		bounceSfx.Play();
	}
}
```

보기에 어떤 생각이 드는가? 사실 나같은 초보자는 별 생각이 없다. <br>
그냥 뭐 움직이이고 부딪히면 소리나는 정도 아닌가? 라는 생각이 들 것이다.<br>

하지만 요약을 봤다면 알 수 있을 것 이다. 이 코드는 움직임도 나타내고, 소리도 나타낸다는 것을 알 수 있다. 고로 이 코드는 `단일 책임 원칙`을 지키지 않은 코드이다.<br>

그렇다면 어떤식으로 바꾸어야 할까? 바로 예시코드 먼저 보여주도록 하겠다.

#### ___단일 책임 원칙 예시코드-2___
```
[RequireComponent(typeof(PlayerAudio),typeof(PlayerInput),
typeof(PlayerMovement))]

public class Player:MonoBegaviour
{
	[SerializeField] private PlayerAudio playerAudio;
	[SerializeField] private PlayerInput playerInput;
	[SerializeField] private PlayerMovement playerMovement;
	
	private void Start()
	{
		playerAudio = GetComponent<PlayerAudio>();
		playerInput = GetComponent<PlayerInput>();
		playerMovement = GetComponent<PlayerMovement>();
	}
}

public class PlayerAudio:MonoBegaviour
{ ... }
public class PlayerInput:MonoBegaviour
{ ... }
public class PlayerMovement:MonoBegaviour
{ ... }
```

어떠한 차이가 있는지 한눈에 알 수 있을 것이다. <br>
왜냐하면 클래스가 그냥 복사가 되 듯 많아졌기 때문이다.<br>
어 뭐야? 이렇게 많아지면 할 것만 많아지고, 더 어려운 것 아닌가요? NoNo 코드를 계속 짜다보면 진짜 내용이 너무너무 많아지고, 계속 추가해야 할 것이 생기기 마련이다.<br><br> 만약 예시-1 코드를 진행했을 경우에는 내용이 늘어나면 늘어날수록 어떤 곳에 어떤 코드를 짰는지 알 수 없을 뿐더러 찾기위해서는 너무나도 눈이 아프더라. 나의 눈이 안좋은 것에 충분한 일조를 했을 것 이다. <br>

주먹구구식이 아닌 이론적으로 이야기를 풀어나가 보자면 이 원칙은

#### __이론적 설명__
- 위와 같이 모든 클래스는 `하나의 책임`만을 가진다.
- 클래스는 그 책임을 완전히 `캡슐화` 해야 한다.
- 클래스가 제공하는 모든 기능은 이 `책임과 부합`해야한다.

`캡슐화` 관해서는 나중에 따로 상세히 설명을 할 것이기에 간단하게 설명하자면 클래스가 그 책임을 너~무 아껴야한다 라고 생각하면 된다.
누구나 소중한 물건, 소중한 것이 있지않은가?  만약 누군가가 빌려달라 했을 때 빌려줘야 한다면 내 눈앞에서, 나를 통해, 이러한 절차가 있는 것과 같다. 이 책임은 무조건 나를 통해서만!

아무튼 단일 책임 원칙은 이정도인 것 같다.

### __개방 폐쇄 원칙(Open-Closed)__

이름만 들었을 때는 모호할 것이다 왜냐 ? 개방이라는 단어와 폐쇄라는 단어는 모순적이기 때문이다. <br>
이름만 듣고 유추한다면 어떠한 것은 개방하고, 어떠한 것은 폐쇄하거나<br>
조건에 관하여 개방과 폐쇄를 정한다 정도는 유추할 수 있을 것 이다.<br>

먼저 위와 같이 코드 먼저 보여주도록 하겠다. <br>
앞으로는 바로 코드를 먼저 보여줄 것이니, 보여준다는 말은 생략하도록 하겠다.

#### ___개방 폐쇄 원칙 예제-1___
```
public class Rectangle
{
	public float width;
	public float height;
}

public class Circle
{
	public float radius;
}

public class AreaCalculator
{
	public float GetRectangleArea(Rectangle rectangle)
	{
		return rectangle.width * rectangle.height;
	}
	public float GetCircleArea(Circle circle)
	{
		return circle.radius * circle.radius * Mathf.PI;
	}
}
```

이 코드 또한 한번 보고 스스로 생각해보기를 바란다.<br>
어떠한 개선점이 있을지 어떤 식으로 작동이 되는지 말이다. <br>
이를 처음 보고 내가 생각한 것은 토글로 감춰놓도록 하겠다. <br>
본인의 생각하는 힘을 위해서 혹은 나중에 내가 봤을 때 어떻게 바뀌었는지를 위해 <br>

<details>
<summary> 필자의 생각 </summary>
<div markdown = "1">
나의 생각은 우선 이런식의 일은 두번 일하는 것 같다. 왜냐하면 다른 도형이 생긴다면 <br>
그 다른 도형에 관한 클래스를 만들고 다시 부피를 구하는 클래스에 메서드를 또 생성해야 하기 때문이다. <br>
그리고 그 메서드는 또 부피에 관하여 적어야한다. 즉 매번 수정하는 것이 2번이라는 말이다. <br>
이 보다는 부피를 구하는 함수는 내버려 두고 각 도형의 클래스에 부피를 구하는 메서드를 넣고,  <br>
부피를 구하는 클래스의 메서드 명은 고정시켜 두는것이 제일 나은 것 같다.

</details>
<br>
그렇다면 다음 예제로 넘어가도록 하자. 

#### ___개방 폐쇄 원칙 예제-2___
```
public abstract class Shape
{
	public abstract float CalculateArea();
}

public class Rectangle:Shape
{
	public float width;
	public float height;
	
	public override float CalculateArea()
	{
		return width * height;
	}
}

public class Circle:Shape
{
	public float radius;
	
	public override float CalculateArea()
	{
		return radius * radius * Mathf.PI;
	}
}

public class AreaCalculator
{
	public float GetArea(Shape shape)
	{
		return shape.CalculateArea();
	}
}
```

나의 생각과 매우 흡사했지만 이는 추상클래스를 사용하여 풀어냈다.
간단하게 나의 생각을 간단하게 설명해보자면 <br>

1. 추상 클래스로 부피를 구하는 추상 메서드를 선언
2. 각 도형들에게 상속시켜, 강제 정의
3. 부피를 구하는 클래스에서 추상클래스를 매개변수 자료형으로 지정
4. 하위 클래스의 도형들을 받아 부피 구하는 메서드를 리턴

이런식으로 수정되어 있다. 이를 보니 override와 같이 쓰이는 virtual가 생각이 나지만
이는 다음에 설명하는 글을 올리도록 하겠다.  <br>

아무튼 이제는 감이 올 것이다. 지금까지 나온 원칙들의 공통점은 바로
이미 만들어 둔 것을 건드리기 싫어한다. 라는 공통점이 말이다. <br>

이미 만들어 둔 것을 건드린 것 만큼 골치아픈 것이 없는 것 같다.

필자도 어떠한 것이 틀어졌을 때 무엇이 문제일지 모르는 그 상황이 너무나도 싫기 때문이다. <br>
그래서 처음부터 다시하는 과정을 몇 번 겪고 나서는 최대한 연계상황들에 대한 간극을 분리시키려는 노력을 한다 <br>
이와 마찬가지인 경우 인 것 같다.  아주 나의 이상적인 방법인 것 같아 흡족하다. <br>

감탄은 여기까지하고 이론적 설명에 관하여 들어보도록 하자.

#### ___이론적 설명___
- 확장에 대해 열려 있어야 한다. ( 기존의 것을 변형하는 것 보단 추가하는 느낌 )
  - 모듈의 동작을 확장 할 수 있어야 한다.
  - 요구 사항이 변경 될 때, 새로운 동작을 추가해 모듈을 확장
  - 모듈이 하는 일을 `유동적`으로 변경할 수 있음
- 수정에 대해 닫혀 있어야 한다. ( 기존의 잘 되던 코드는 두고, 확장하고 수정)
  - 코드를 수정하지 않아도 모듈의 기능을 확장하거나 변경 가능
  - 모듈의 라이브러리의 수정이필요 없음
  
갑자기 이론적 설명을 들으니 정신이 벙벙하다 그쵸? 저는 그럽니다 하하하. <br>
일단 저의 생각은 간단합니다. 

기존 작성한 것들에 대하여 최대한 수정 없이 진행할 수 있어야 한다. <br>
작성한 것에 대한 추가사항은 수정이 아닌 확장을 통해 진행되어야 한다. <br>
입니다. 아무튼 훌륭한 원칙인 것 같다. <br>
이론적 설명이 나오다 보니 갑자기 존댓말로 글을 써내려간 것이 조금 어색하지만 그냥 넘어가자.

그럼 이 상황에 맞춰 다음으로 넘어가도록 하자.

### __리스코프치환(Liskov Substitution)__

아까는 이름으로 유추해보았지만 난생 처음듣는 단어이다. 유추가 되지 않는다.<br> 
알고 봤더니 그냥 사람 이름이였다. 아주 훌륭한 사람이니 이렇게 이름으로 쓰여지고 있는 것일게 분명하다. <br>
혹시나 관심이 있다면 이 사람은 내가 따로 태그를 만들어 첨부 하겠다.

그렇다면 바로 예제로 가겠다.

#### ___리스코프치환 예제-1___
```
public class Vehicle
{
	public float speed = 100.0f;
	
	public Vector3 direction;
	
	public void GoForward()
	{ ... }
	public void Reverse()
	{ ... }
	public void TurnRight()
	{ ... }
	public void TurnLeft()
	{ ... }
}
```

이 예제는 Vehicle 즉 탈 것에 대한 클래스이다. <br>
간단한 전진, 후진, 좌회전, 우회전 메서드가 있는데 어떤 것이 이상할까? <br>
솔직히 나는 아무 생각이 없었다. 뭐 탈 것이라면 원래 이렇게 있지 않은가? 라는 생각 <br>
내가 지방사람이라서 그런 것일 확률이 더 높은 느낌이다 ㅋㅋ <br>
경기도 혹은 서울, 광역시에 거주하는 사람들이라면 눈치를 챘을 수 있겠지만 <br>
예외사항은 바로 지하철이다. 지하철은 앞만 가지 않는가? 아니 뒤도 가는가? <br>
일단 구조상으로는 앞과 뒤를 갈 수 있을 것 같다. 레일을 통해 가는 것이니 말이다. <br>
<br>
그렇다면 어떤식으로 개선이 되어야 할 것일까? 그냥 클래스를 더 상세히 나눠야 하는 것 일까? <br>
앞뒤만 갈 수 있는 교통수단과 둘 다 허용되는 교통수단 이렇게 말이다. <br>
<br>

역시나 필자의 예상을 틀리지 않았다. 모자랐을 뿐이지 하하하..ㅋㅋ <br>
구별 될 동작을 interface로 나눠주고, 이를 받아갈 클래스를 나눠준 것 같다. <br>
아까 요약에서 본 것과 같은 맥락으로 볼 수 있다. <br>

상속받은 클래스는 부모 클래스의 방향성을 지켜야하기 때문에. 역으로 생각하자면 <br>
방향성을 꼭 지킬, 필요한 것만 상속시킬 필요가 있다. 그렇기에 기능을 구분하여 인터페이스를 두개로 나눈 것 이다. <br>

사실 이에 대해서는 필자의 생각은 조금 당연한 말을 하는 것 아닌가? 싶기도 하지만 내가 만들고, 짠 코드들은 그렇지 않더라 <br>
그렇기에 조금 더 면밀히 따져봐야 할 것 같다.

그렇다면 바로 이론적 설명으로 넘어가겠다. 이제는 속도가 붙었을테고, 나름 이해했다고 생각한다.

#### __이론적 설명__
- 파생 클래스는 기본 클래스를 대체할 수 있어야 한다.
  - 상속받은 클래스는 부모 클래스의 `방향성`을 지켜야 한다.
- 하위 클래스는 강력하고, 유연하게 만드는 원칙
- OOP의 상속을 사용하면 하위 클래스를 통해 기능을 추가 가능
  - 그러나 주의하지 않으면 불필요한 복잡성 발생
<br>
여기에 그치지 않고 리스코프치환은 유의사항 또한 나열하도록 하겠다. 

#### __유의사항__
- 서브클래싱할 때 기능을 제거하는 경우 리스코프치환원칙을 위배 (방향성)
  - 부모 클래스의 상속받은 기능을 제거(무효화)하는 경우를 뜻함
- 추상화를 단순하게 유지
- 하위클래스에는 기본 클래스의 퍼블릭 멤버가 존재
- `상속` 보다는 `구성`

- 클래스 계층 구조를 설정하기 전에 클래스 api를 고려
  - 현실의 분류가 항상 클래스의 계층 구조로 변환되는 것은 아님
  - Ex) Car와 Train이 별도의 상위 클래스에서 상속받는 것이 합리적인 것 처럼

나의 모자란 지식으로 간단한 비유를 곁들여 설명해보자면 <br>
일단 콩심은 데 콩나고 팥심은 데 팥난다 라는 말이 있듯 <br>

### __인터페이스 분리 원칙(Interface Segregation)__

#### ___인터페이스 분리 원칙 예제-1___
```
public interface IUnitStats
{
	public float Health {get;set;}
	public int Defense {get;set;}
	public void Die();
	public void TakeDamage();
	public void RestoreHealth();
	public float MoveSpeed{get;set;}
	public float Acceleration{get;set;}
	public void GoForward();
	public void Reverse();
	public void TurnLeft();
	public void TurnRight();

	public int Dexterity {get;set;}
	public int Endurance{get;set;}
```

이 어지럽고도 험악한 코드가 보이는가? 이게 대체 뭐하는 짬뽕밥인지 모르겠다. <br>
물론 각각의 메서드가 무엇을 나타내는지는 대충 유추가 간다 하지만 인터페이스 특성 상 상속받은 클래스가 모든 것을 정의해야하는데 이건 무슨 낭비인가? <br>

- 시스템의 내부 의존성을 약화하고 유연성을 강화한다.

### __의존 역전 원칙(Dependency Inversion)__

의존 역전 원칙.. 이름부터 대충 감이 오지않는가? 하극상 하지말라 이말이야! 이런느낌..ㅋㅋㅋ<br>
대충 의존을 받아야 할 것이 오히려 의존을 하는 경우를 이야기하는 것 같다.<br>
상속이나 아니면 연계되는 동작들에 관하여? 인 것 같은데 바로 예제로 넘어가자.

#### ___의존 역전 원칙 예제-1___
```
public class Switch:MonoBehaviour
{
	public Door door;
	public bool isActivated;
	public void Toggle()
	{
		if(isActivated)
		{
			isActivated = false;
			door.Close();
		}
		else
		{
			isActivated = true;
			door.Open();
		}
	}
}
public class Door:MonoBehaviour
{
	public void Open()
	{
		Debug.Log("Ther door is open.");
	}
	public void Close()
	{
		Debug.Log("The door is closed.");
	}
}
```
코드를 한번 쭈욱 보고 이상한 것이 있다면 혼잣말로라도 말해주길 바란다.
필자의 생각은 아까와 같이 토글로 숨겨두도록 하겠다.<br>

#### ___의존 역전 원칙 예제-2___
```
public interface ISwitchable
{
	public bool IsActive {get;}
	public void Activate();
	public void Deactivate();
}

public class Door:MonoBehaviour,ISwitchable
{
	private bool isActive;
	public bool IsActive => isActive;
	public void Activate()
	{
		isActive = true;
		Debug.Log("The door is open.");
	}
	public void Deactivate()
	{
		isActive = false;
		Debug.Log("The door is closed.");
	}
}

public class Switch:MonoBehaviour
{
	public ISwitchable client;
	
	public void Toggle()
	{
		if(client.IsActive)
		{
			client.Deactivate();
		}
		else
		{
			client.Activate();
		}
	}
}
```
캬 다들 이렇게 생각하고 있었는가? 물론 나는 이렇게 완벽하게 생각하지는 않았지만 <br>
대충 이런느낌이다 라는건 거짓말이 아니다. <br>
먼저 코드를 확인해보자면 그렇게 어렵지 않다, 보는 바와 같다. <br>
뭐라고 코드에 관하여 더 설명할 것이 없다고 생각이 든다.
고로 바로 이론적설명으로 넘어가도록 하겠다.

#### __이론적 설명__
- 소프트웨어 모듈들을 분리하는 특정 형식이다.
- 상위 모듈은 하위 모듈의 것을 `직접` 가져오면 안된다.
  - 둘 다 `추상화`에 의존해야 한다.
- 추상화는 세부 사항에 의존해서는 안된다.
  - 세부사항이 추상화에 의존해야 한다.
- 클래스가 다른 클래스와 관계가 있으면 안된다.
  - 클래스가 다른 클래스의 작동 방식을 많이 알고 있으면 안된다.
  - 종속성 또는 결합이 발생한다.
  - 종속성은 어느 잠재적인 위험이 발생할 수 있다.
    - 한 클래스를 수정하면 관계가 있는 다른 클래스도 수정 해야 하는 상황이 발생할 수 있다.
  ![image](Dependency.png)
  -> 참조를 해야 한다면 `추상화`를 통해 참조하는 것이 좋다.

언제나 이론적 설명을 보자면 내가 이해했던게 맞나? 라는 생각이 들 때가있다. <br>
하지만 보고있는 당신 혹은 미래의 내가 생각하는 그것이 맞을 것이다. <br>
왜냐하면 우리는 이미 겪어본 상황일 확률이 매우매우 높다. <br>
그리고 그러한 상황이 나오는 횟수가 줄어들고 있을 것이다. <br>
그것만 해도 당신은 현재 이것을 인지하고 있다고 생각한다. <br>
<br> <br>
이렇게 SOLID원칙 5가지를 알아보았다.

이해가 됐을 수 도 있고, 안됐을 수 도 있다.
